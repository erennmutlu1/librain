Appendix B. November 2026 revision

Added on 18 November 2026. Pages 1–65 are unchanged from the revision archived on Zenodo (DOI 10.5281/zenodo.20745782). This appendix records what has changed in the software since then, corrects two statements made in the main text, and reports a further set of Discovery runs. All numbers below are computed from files committed to the repository; the paths are given in B.8.

B.1 Scope of the revision

The work summarised here falls into four groups: corrections to two reported figures (B.2), engineering changes that make the pipeline fail loudly instead of silently (B.3), verification that the committed results still reproduce under the changed code (B.4), and an interface and deployment layer that turns the research prototype into something a reader can run and inspect (B.5). Section B.6 then reports Experiment 8, 46 new Discovery runs, and B.7 lists the limitations that the new runs make clearer. Prompts, models, temperatures and the request bodies sent to the model API were deliberately left unchanged, so new runs remain comparable with the experiments in Sections 6 and 7.

B.2 Corrections to the main text

Fabricated-citation count (RQ3). The main text reports 67 fabricated citations surfaced by the contract-free baseline. The correct figure is 65 to 67. In two of the counted answers (pair-01, starved corpus, gpt-4o-mini, at both coercion levels) the model cited a passage by echoing the prompt's own source header, [paper_id=deepdta chunk_index=0]. The free-text parser of the time could not read that form and counted it as a fabrication. Whether chunk 0 of deepdta was in those runs' retrieval sets was not recorded, so each of the two may or may not be a fabrication. The parser now reads the echoed form. Replaying it over all 40 committed free-text answers gives the same number of claimed citations as committed (151) in every file. LIBRAIN's own count of zero is unaffected, and so is the conclusion of Section 7.

Prompt caching. Sections 7.3 and 8.4.B treat prompt caching as a lever for per-query cost, and the repository README described it as active on every agent with roughly 80% of the static prefix reused. It is enabled on every agent, but measured over the 46 runs of Experiment 8 it took effect only for the Sonnet 4.6 generation call, where 11.4% of prompt tokens were read from cache. The two Haiku 4.5 calls per run (the Discovery Evaluator and the Claim Validator) were never cached, because their system prompt and tool schema are shorter than the minimum prefix length the API will cache. Caching therefore does little to lower the cost estimates in Section 7.3; the measured cost of a Discovery run is given in B.6.

B.3 Engineering changes

An audit of the pipeline code found several places where a failure was turned into a plausible-looking number rather than an error. Table B.1 lists the changes. None of them alters a committed result: B.4 describes how this was checked.

Table B.1. Changes since the archived revision
ChangeWhat it prevents
Claim validation fails closedA validator reply with no usable per-sentence verdict used to aggregate to risk 0. It is now marked validationFailed with risk 1.0, and a RISKY verdict without a probability counts at the band floor (0.6), not 0.
Judge scores are requiredA missing or non-numeric plausibility or coherence score used to be recorded as 0, pulling averages down. It is now an error.
One Discovery contract for both providersThe OpenAI port carried its own copy of evidence and basis validation, which had drifted: it invented a pure_speculation basis entry where the Anthropic path rejected the response. No committed result contains the invented entry.
Lenient reading of model JSONA value of the wrong JSON type ("3" for 3, a numeric paper id) failed the whole request with a 502. It is now coerced, or the entry is dropped and counted.
Truncation detection; 4,096-token ceilingReplies cut off at the old 1,024-token limit were parsed as if complete. They are now rejected. Billing is per generated token, so the higher ceiling costs nothing for replies that already fit.
Retries with backoffA single rate-limit or overload response ended a four-call run. Transient errors are retried up to three times; timeouts are not, so a request cannot be billed twice.
Re-ingest removes stale chunksRe-ingesting a paper that had become shorter left its old trailing chunks in the index, where retrieval kept finding them.
Provider-neutral interfacesAgents now depend on narrow interfaces for the language model, the embedding model and the vector store, so the full pipeline runs in tests against recorded or fake responses with no network access.

B.4 Verification against committed results

Because the changes touch scoring and validation, the committed results were used as a regression check. Each of the 30 Discovery outputs in experiments/discovery-openai/ is replayed through the current pipeline, with the model's recorded outputs supplied in place of live calls and the recorded nearest-neighbour similarity supplied to the novelty scorer. For all 30, quality, novelty and aggregate claim risk match the committed values to within 10−5, and the citation contract keeps exactly the committed evidence and basis entries. The replay found one defect of its own: numeric values constructed in code, rather than parsed from model text, were not read by the new JSON helpers. It was fixed before any result was reported. The full backend suite now has 237 tests, which run in continuous integration together with an integration test against a real Qdrant instance and 173 tests of the web interface.

B.5 Interface and deployment

Section 8.4.B deferred an interactive frontend and response streaming to Phase 3.B. Both now exist, built as a React and TypeScript application rather than with Next.js or Blazor, and run locally or through Docker Compose; the Azure deployment in the same list is still outstanding. The interface lists the corpus, answers questions with citations that open at the cited passage, shows every novelClaim sentence coloured by its verdict, compares LIBRAIN with the two baselines on one topic pair, and keeps a history of runs. Completed runs are stored in SQLite under their correlation identifier, which serves as the per-output audit lookup that the project plan specified as GET /api/audit/{id}. Long runs report their progress as server-sent events. Papers can be ingested by arXiv identifier, in which case title, authors and year come from the arXiv API rather than from the PDF metadata. A Docker Compose file starts Qdrant, the API and the interface together. For a public deployment (Section 9), an optional API key and a per-client hourly limit on every endpoint that calls a model protect the API budget.

B.6 Experiment 8: Discovery runs in new fields

Goal. Run Discovery Mode on topic pairs chosen at the level of specific mechanisms rather than broad fields, across fields the original corpus did not cover, and measure how often the outputs pass LIBRAIN's checks after the changes in B.3.

Setup. 46 runs on 46 distinct topic pairs, in two batches. The first 21 bridged drug discovery with agentic systems, agriculture and energy with foundation models, and clinical trials with causal and graph methods, plus three new pairings, against the 41-paper corpus. For the second batch of 25, 14 arXiv papers were added (corpus 55 papers, 2,210 chunks; every title was checked against the arXiv API before ingest), covering football, sport, web development, programming languages and labour-market studies. Each pair joined a new paper to one already in the corpus. Models, prompts and parameters were those of Sections 3 and 6: Claude Sonnet 4.6 generates, Claude Haiku 4.5 judges and validates claims, topK = 5. Cost was computed from the token counts the API logs, and each batch had a hard cap of US$2. A sixth requested field, how people would live without money or work, was not run: as stated it is a question of values and policy that a literature-grounded tool cannot settle, and its researchable part, the effect of AI on jobs, is covered by the labour-market pairs. Featured results were chosen by reading every output, not by score: a specific mechanism, a testable consequence, and evidence drawn from more than one paper.

Result. Every run completed and no fabricated citation reached the output. Unlike the cross-family study for RQ3, the contract had nothing to remove: with a strong model and structured tool output, all 246 claimed citations resolved. This agrees with Section 7.6, where Sonnet 4.6 produced no fabrications across 44 Naive-RAG citations and fabrication appeared only with weaker models, free-text citations or starved retrieval, which is where the contract earns its place. The validator flagged four sentences, and in each case the flag sits on a confident quantitative or capability claim, such as D1's statement that a combined system would exceed PharmAgents' reported 37.94% success rate. The highest quality scores came from the new fields: F2 (player-action values in football with graph attention, 0.665), W5 (front-end benchmarks as teaching material, 0.660) and S3 (training-load injury forecasting with probabilistic time-series models, 0.647, the highest novelty of all runs at 0.541). Examples of the 14 featured results are F4, which treats players at a corner kick as particles in a learned physics simulator so that a tactics assistant could evaluate whole movement plans, and C1, which turns compartmental epidemic equations into features that an LLM agent can search over when predicting trial outcomes. Each is a candidate hypothesis; none has been tested.

Observations. Two properties of the scores limit what Table B.2 can show. First, the LLM judge is coarse: across 46 runs, plausibility took only six distinct values (0.28, 0.35, 0.42, 0.62, 0.68, 0.72) and structural coherence seven, so small differences in quality are mostly differences in novelty. Second, novelty is measured as cosine distance to the nearest chunk of a 55-paper corpus. The highest-scoring run of the first batch (A6, vision-transformer patch embeddings for satellite crop monitoring) was not featured because the idea is an established research direction outside the corpus; the metric cannot see that. Reading the outputs also shows a recurring template: most hypotheses propose combining a mechanism from one paper with a problem from another, and few make a surprising prediction.

B.7 Limitations and next steps

The new runs make four limitations of the current design more concrete. Novelty is relative to the corpus, and agrees only moderately with human novelty ratings (pooled Spearman ρ = 0.41, Section 7.6), so a literature-wide novelty check, for example a search of arXiv or Semantic Scholar for the proposed mechanism, is the most useful next addition. No hypothesis carries a testable prediction; requiring each to state an experiment, an expected result and what would refute it would make the outputs easier to act on and to judge. The judges are themselves language models with a coarse scale, so several judges with a finer rubric, and a panel of domain experts for a sample of outputs, would make the scores more informative. Finally, each run is a single sample, and the model generation used here predates the current one; repeating a subset with newer models, which requires replacing forced tool calls and fixed temperatures, would show how much of the result depends on the model. Retrieval remains plain dense top-k; hybrid keyword and vector search with re-ranking is the main retrieval change still outstanding.
